# NetAnim guide for the defence

This note explains what the network animation files are, how to open them, and
what to point at while presenting. It assumes the project is at
`/home/ksschkw/Projects/fyp`.

## What NetAnim is

Network Animator (NetAnim) is a desktop program that plays back an animation
trace produced by ns-3. The trace is a large XML file written by the ns-3
`AnimationInterface` class while a simulation runs. The XML records node
positions, link topology, and packet movements. NetAnim reads that XML and
draws the nodes and moving packets on a timeline.

NetAnim does not run the simulation. It only replays a file. The simulation
must have been run once with `AnimationInterface` enabled to produce the file.

## Where the program and the files are

- Program: `netanim/build/netanim` (already built, all libraries present).
- M1 two-flow animation: `docu/m1-network-sandbox/results/dumbbell-tcp-animation.xml`
- M2 four-flow animation: `docu/m2-congestion-dynamics/results/multi-flow-animation.xml`
- MARL two-agent animation: produced after training, see the section below.

## How to open an animation

From a terminal on the desktop session:

```bash
cd /home/ksschkw/Projects/fyp
./netanim/build/netanim docu/m2-congestion-dynamics/results/multi-flow-animation.xml
```

Or start NetAnim with no file and use File, then Open:

```bash
./netanim/build/netanim
```

If NetAnim refuses to start with an error about the Qt platform plugin, you are
probably running it from a shell without a desktop session (for example over
plain SSH). Run it from the Linux Mint desktop, or prefix the command with
`QT_QPA_PLATFORM=xcb`.

## What you will see, and what to point at

When the M2 animation loads, you get six nodes laid out left to right: four
senders on the left, two routers in the middle, four receivers on the right.
The two routers are joined by the shared bottleneck link. Press the play button
on the toolbar to start playback, and use the time slider to move through the
60 second run.

Things worth pointing at during the defence:

1. The middle link carries packets from all four senders at once. This is the
   10 Mbps bottleneck, and it is the only shared resource in the experiment.
2. The packets on the middle link are dense and continuous. The link is close
   to fully used, which matches the measured total throughput near 9.95 Mbps.
3. The senders do not take equal shares over time. The CUBIC senders push more
   packets than the BBR sender. This is the unfairness that the M2 notes record
   as a Jain index of 0.9818 and that motivates the multi-agent approach.
4. Because DropTail queues drop only when the buffer is full, most packets still
   arrive. Loss is visible only as occasional gaps, not as a collapse.

## How an animation file is produced

Any ns-3 program can write one. In `docu/m1-network-sandbox/code/dumbbell-tcp.cc`
this block does it:

```cpp
#include "ns3/netanim-module.h"
...
std::string animFile = "dumbbell-tcp-animation.xml";
AnimationInterface anim (animFile);
anim.SetConstantPosition (senders.Get (0), 0.0, 10.0);
anim.SetConstantPosition (routers.Get (0), 30.0, 20.0);
anim.SetConstantPosition (receivers.Get (0), 90.0, 10.0);
```

The `SetConstantPosition` calls only fix the drawing coordinates. Without them
ns-3 assigns positions automatically and the picture is less readable.

The file is written when the simulation finishes. A 60 second run with full
packet metadata produces several megabytes, which is normal.

## Producing a MARL animation

The multi-agent program has an `--anim` switch. It writes
`marl-multi-animation.xml` in the ns-3 directory. Run it for a short episode so
the file stays small:

```bash
cd /home/ksschkw/Projects/fyp/ns-3-dev
./ns3 run "marl-multi-tcp --duration=5 --anim=1 --flowmon=1 --openGymPort=5555"
```

That command needs the Python side attached, so in practice the file is
generated by the evaluation helper in `rl_agent/m5_evaluate.py` with
`--anim`, or by running the program through the ns3-gym bridge. The resulting
file is copied to `docu/m5-evaluation/results/marl-multi-animation.xml`.

The MARL layout is the same dumbbell as M1: two sender nodes, two routers, two
receivers. The point to make with the MARL animation is that both senders keep
the bottleneck busy at the same time, because the shared policy was rewarded
for fairness as well as throughput.

## Troubleshooting

- Blank window or immediate exit: check that a display is available
  (`echo $DISPLAY` is not empty) and that you are on the desktop session.
- "Could not find the Qt platform plugin xcb": install
  `libxcb-xinerama0` (Linux Mint package) or run with `QT_QPA_PLATFORM=xcb`.
- Animation file is too large to open: rerun the simulation with a shorter
  `--duration`, or add `anim.SetMaxPktsPerTraceFile(500000);` before the run.
